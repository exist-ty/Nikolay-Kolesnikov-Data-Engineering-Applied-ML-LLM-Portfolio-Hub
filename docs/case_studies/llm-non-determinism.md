# Case Study: повторный прогон LLM-триажа дал другую accuracy

## Problem

[`support-triage-llm/scripts/evaluate_llm.py`](https://github.com/exist-ty/support-triage-llm/blob/main/scripts/evaluate_llm.py) сравнивает предсказанную моделью
(`qwen2.5:3b-instruct`, Ollama) категорию обращения с известной по
построению синтетических данных `true_category`. Первый честный прогон дал
accuracy 0.69 (чистый векторный поиск), затем 0.71 (после перехода на
гибридный RRF-поиск — см. [`docs/adr/003-why-rrf-hybrid-search.md`](../adr/003-why-rrf-hybrid-search.md)). При
подготовке этого хаб-репозитория `evaluate_llm.py` был прогнан ещё раз на
том же самом коде и том же датасете (без единого изменения в логике
триажа) — и дал 0.73, не 0.71.

## Investigation

Три возможных объяснения были рассмотрены: (1) регрессия в коде между
прогонами — исключено, `git diff` между прогонами по `support-triage-llm`
не затрагивал ни `src/rag.py`, ни `src/triage.py`, ни промпт; (2) разные
входные данные — исключено, `client_messages`/`true_category` строится
детерминированно тем же `generate_messages.py` с фиксированным сидом; (3)
недетерминированность самого вызова LLM — Ollama `/api/generate` не
получает явный `seed`/`temperature=0` от `src/ollama_client.py`, значит
дефолтная температура сэмплинга даёт разный текст на одном и том же
промпте между запусками.

Дополнительно изменился канал с наибольшей долей жалоб между двумя
прогонами (`referral` 25% в одном, 12.5% в другом, `context_ads` — 20%) —
согласуется с гипотезой (3): при n=45 сообщениях небольшие сдвиги в
классификации нескольких пограничных случаев ощутимо двигают долю по
категориям с малым числом наблюдений.

## Solution

Это не баг, который нужно чинить программно (жёстко зафиксировать
`temperature=0`/`seed` — было бы искусственным устранением реального
свойства системы, а не решением проблемы измерения). Вместо этого —
честная документация: README `support-triage-llm` и хаба прямо называют
неопределённость воспроизводимости отдельным задокументированным риском, а
не скрывают её за единственным "финальным" числом. [`n8n-business-automation/docs/manager-guide-self-service-bot.md`](https://github.com/exist-ty/n8n-business-automation/blob/master/docs/manager-guide-self-service-bot.md)
(соседний компонент, тот же класс модели) отдельно убрал из списка
"гарантированно работающих" примеров вопрос, на который модель однажды
ответила верно, а затем — `NOT_POSSIBLE`, вместо того чтобы скрыть
нестабильность за одним удачным прогоном.

## Lesson Learned

Для маленьких инференс-моделей без фиксированного сида "одно измерение"
статистически не то же самое, что "воспроизводимый результат" — n=45
сообщений и недетерминированный сэмплинг означают, что каждый прогон
`evaluate_llm.py` — это одна точка из распределения возможных исходов, а
не единственно верное число. Правильная реакция — не пытаться получить
"стабильное" число подгонкой (фиксацией сида ради красивой воспроизводимости
в презентации), а явно указать диапазон наблюдавшихся значений (0.69–0.73)
и объяснить механизм, из-за которого он существует. Тот же дисциплинированный
принцип, что и в честном power-анализе A/B-теста: отсутствие "одного
надёжного числа" — не провал измерения, а свойство системы, которое стоит
показать, а не спрятать.
