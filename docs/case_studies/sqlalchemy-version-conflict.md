# Case Study: конфликт версий SQLAlchemy между Airflow и задачными скриптами

## Problem

Первый прогон `etl_pipeline` внутри Airflow упал с `ImportError` на строке
`from sqlalchemy import Engine` в [`etl-portfolio/src/etl/db.py`](https://github.com/exist-ty/etl-portfolio/blob/master/src/etl/db.py). Скрипт
работал локально (вне Airflow) без единой проблемы — тот же файл, тот же
Python, разное окружение.

## Investigation

Задачные зависимости (`pandas`, `sqlalchemy`, `clickhouse-connect` и т.д.)
изначально ставились прямо в Python-окружение самого Airflow, с
`--constraint` из официального constraints-файла Apache Airflow 2.10.4 —
стандартная, рекомендуемая практика для установки дополнительных пакетов
поверх образа `apache/airflow`.

Проверка версии в контейнере (`pip show sqlalchemy`) показала `1.4.54` —
не то, что было в `requirements.txt` (`sqlalchemy>=2.0`). Constraints-файл
Airflow тихо зафиксировал версию ниже запрошенной. Причина: Airflow 2.x
жёстко требует `sqlalchemy<2.0` — на этой версии держится
`flask-appbuilder`/`marshmallow-sqlalchemy`, а через них — весь
веб-интерфейс Airflow. `Engine` как экспортируемый тип верхнего уровня
появился в SQLAlchemy 2.0 — в 1.4 такого импорта просто не существует,
отсюда `ImportError`, а не более туманная ошибка времени выполнения.

## Solution

Отдельный `venv` для задач, полностью изолированный от Python-окружения
самого Airflow: `python -m venv /home/airflow/task-venv` на этапе сборки
образа (`Dockerfile`), зависимости ставятся туда, а не в системный
`python`. DAG (`ecosystem_pipeline_dag.py`) вызывает
`/home/airflow/task-venv/bin/python`, а не `python`/`python3` напрямую —
`BashOperator`-задачи явно указывают путь к бинарнику task-venv.

Тот же класс проблемы всплыл повторно при добавлении MLflow: клиент,
поставленный в `task-venv` без явного пина, подтянул более новую версию
(3.14.0), чем образ сервера (`v2.19.0`), и упал на несовместимом API-вызове
при завершении run. Решение то же по духу — явный пин версии в
`requirements-tasks.txt` (`mlflow==2.19.0`), а не "поставится — разберёмся".

## Lesson Learned

"Стандартная, рекомендуемая практика" (constraints-файл официального
образа) может тихо понизить версию пакета до конфликта с реальным кодом —
проверять фактически установленную версию в целевом окружении надёжнее,
чем доверять `requirements.txt` без верификации. Второй случай (MLflow)
показывает, что урок не разовый: любая зависимость, установленная в общее
или недостаточно изолированное окружение без явного пина, рискует
разъехаться с версией, под которую написан код, вызывающий её. Общее
архитектурное решение (изоляция через отдельный venv, ADR 005) закрыло
класс проблем, а не один конкретный случай — но каждая НОВАЯ зависимость
внутри этого venv всё равно требует своего явного пина, если у неё есть
внешний "партнёр" (в данном случае — сервер MLflow), версию которого нужно
match'ить.

См. [`docs/adr/005-why-separate-venv-for-tasks.md`](../adr/005-why-separate-venv-for-tasks.md).
