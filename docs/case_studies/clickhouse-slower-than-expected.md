# Case Study: ClickHouse оказался медленнее Postgres на этом объёме данных

## Problem

[`product-marketing-analytics`](https://github.com/exist-ty/product-marketing-analytics) уже имел Postgres VIEW `mart_channel_economics`
для агрегата "выручка по каналу/месяцу" — пересчитывается целиком на каждый
`SELECT`. Добавлен ClickHouse-слой (`analytics.order_events` — `MergeTree`,
плюс `channel_monthly_revenue` — `AggregatingMergeTree` с инкрементальным
`MATERIALIZED VIEW`) как демонстрация OLAP-профилирования. Ожидание "по
умолчанию" для колоночного движка — что он окажется быстрее.

## Investigation

`clickhouse/compare_engines.py` прогоняет один и тот же логический запрос
(агрегат "выручка по каналу/месяцу") тремя способами: (1) Postgres VIEW,
пересчёт с нуля; (2) ClickHouse, агрегация сырых `order_events` с нуля; (3)
ClickHouse, чтение уже посчитанного `channel_monthly_revenue` через
`-Merge`-комбинаторы. Каждый вариант — медиана из 20 прогонов после одного
warmup-прогона (`median_wall_time_ms`), на реальных 1985 заказах после
очистки данных.

Результат:

| Способ | Медианное время |
|---|---|
| Postgres VIEW (пересчёт с нуля) | 2.1 ms |
| ClickHouse, агрегация с нуля | 13.2 ms |
| ClickHouse, инкрементальный rollup | 5.3 ms |

Postgres быстрее ClickHouse во всех трёх вариантах — включая собственную
инкрементальную витрину ClickHouse, у которой агрегат уже частично посчитан
на этапе вставки. Не ошибка измерения (проверено: warmup-прогон исключён,
медиана, а не единичный замер, сеть между сервисом и БД одна и та же).

## Solution (объяснение, не "починка")

Здесь нечего чинить — результат корректен и объясним. Колоночный движок
ClickHouse платит фиксированную цену за каждый HTTP-запрос (в отличие от
persistent-соединения Postgres в рамках одного бенчмарка), и то, что
итоговый агрегат — всего 60 строк, меньше, чем накладные расходы движка,
спроектированного сканировать миллиарды строк. Реальное преимущество
`MergeTree`/колоночного хранения и инкрементальных агрегатов проявляется на
объёмах, которые физически не помещаются в план Postgres целиком в память
или требуют полного пересканирования при каждом запросе — не на 2000
строках синтетического пет-проекта.

## Lesson Learned

"Технология X обычно быстрее для задач такого типа" — утверждение про
асимптотику на масштабе, а не гарантия на любом конкретном объёме данных.
Честный бенчмарк на реальных, пусть и маленьких, данных — единственный
способ узнать, где именно проходит точка перехода, вместо того чтобы
предполагать её по общей репутации технологии. Ценность демонстрации здесь
осталась архитектурной (правильно спроектированный `ORDER BY`/
`PARTITION BY`/инкрементальный rollup — то, что имеет значение при
реальном масштабе), а не "измеренным ускорением", и README прямо говорит
об этом, а не подгоняет вывод под ожидаемое "ClickHouse быстрее".
