# ADR 003: RRF-гибридный поиск на pgvector, не чистый вектор и не отдельная vector DB

## Context

RAG-триаж ([`support-triage-llm`](https://github.com/exist-ty/support-triage-llm)) должен находить релевантные документы базы
знаний (`kb_documents`) для входящего обращения клиента. Два независимых
вопроса: (1) чисто векторный поиск или гибрид (dense + sparse); (2)
pgvector рядом с уже существующим Postgres или отдельная vector DB
(Pinecone/Milvus/Weaviate).

## Decision

**Гибридный поиск**: dense (pgvector, cosine similarity) + sparse
(Postgres full-text, `ts_rank`), объединённые через Reciprocal Rank Fusion
(`k=60`, константа из оригинальной статьи Cormack/Clarke/Buettcher 2009,
не подобрана под этот датасет — см. `src/rag.py::reciprocal_rank_fusion`).

**pgvector**, не отдельная vector DB — данные (`kb_documents`,
`client_messages`, `triage_results`) и так живут в Postgres, извлечение в
отдельный сервис добавило бы сетевой хоп и вторую систему без выигрыша при
таком объёме документов (десятки, не миллионы).

## Consequences

- **Гибрид дал измеримое, но неоднозначное улучшение**: accuracy 0.69→0.71,
  weighted F1 0.61→0.64, но macro F1 просел 0.64→0.62 — не однозначное
  улучшение по всем метрикам, а перераспределение ошибок (см. README
  [`support-triage-llm`](https://github.com/exist-ty/support-triage-llm), "Оценка качества"). Задокументировано честно, а не
  представлено как чистая победа.
- **RRF не чинит ошибки понимания моделью**: `cancel`→`return` осталось
  100% ошибочным и после перехода на гибрид — потому что причина не в
  retrieval (какой документ нашли), а в том, как 3B-модель интерпретирует
  два близких по смыслу интента (см. ADR 002). Гибридный поиск — это
  улучшение retrieval-слоя, не панацея для reasoning-слоя.
- **pgvector масштабируется хуже специализированной vector DB** на
  миллиардах векторов/высоком QPS с приближённым поиском (HNSW-индексы
  специализированных движков обычно быстрее на таком объёме) — но при
  десятках документов базы знаний этого пет-проекта разница ненаблюдаема,
  а вторая инфраструктурная система была бы преждевременной сложностью.
- **Когда пересматривать**: рост базы знаний до сотен тысяч+ документов
  или требование высокого QPS с низкой задержкой — тогда стоит
  переоценить отдельную vector DB с ANN-индексами.

## Status

Accepted.
